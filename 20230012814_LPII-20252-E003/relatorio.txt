Questão 1
---------
Por que os pacotes UDP enviados antes do servidor iniciar são perdidos?
E por que o cliente HTTP (TCP) falha imediatamente sem servidor?

  UDP é um protocolo sem conexão e sem estado. O cliente simplesmente escreve
  os datagramas na pilha de rede — se não existe processo escutando na porta
  de destino, o sistema operacional do servidor descarta silenciosamente os
  pacotes (ou devolve um ICMP Port Unreachable que o cliente, por padrão,
  ignora). Como não há handshake, o cliente nunca sabe que não há ninguém
  do outro lado.

  TCP exige o handshake de 3 vias (SYN → SYN-ACK → ACK) antes de qualquer
  dado ser enviado. Se não há processo ouvindo na porta, o sistema operacional
  responde com um RST (reset) ao SYN do cliente. A chamada connect() detecta
  esse RST e retorna imediatamente com erro "Connection refused". Sem conexão
  estabelecida, não há como enviar dados — a falha é obrigatória e imediata.

Questão 2
---------
O cliente UDP detecta a queda do servidor? E em uma conexão TCP?

  UDP: NÃO. A queda do servidor é invisível para o cliente. sendto() nunca
  bloqueia esperando confirmação; ele apenas entrega o datagrama ao kernel,
  que tenta transmiti-lo. Se o destinatário sumiu, o pacote é simplesmente
  descartado. Sem ACK, sem timeout, sem erro retornado ao processo. O cliente
  continua enviando alegremente para o vazio.

  TCP: SIM. A conexão TCP é um estado mantido pelos dois lados. Quando o
  servidor cai abruptamente (sem enviar FIN), o cliente eventualmente detecta
  a queda de uma de duas formas:
    a) Ao chamar recv(): retorna 0 se o servidor fechou normalmente (FIN),
       ou -1 com errno=ECONNRESET se a conexão foi resetada.
    b) Ao chamar send(): se o servidor não responde aos ACKs, o TCP do cliente
       detecta timeout e encerra a conexão, retornando erro.
  Isso é possível porque o TCP mantém um canal bidirecional com estado e
  keepalive. O UDP não tem nenhum conceito equivalente.

Questão 3
---------
O que faz a comunicação ser "HTTP" no http_client.c?

  O que diferencia HTTP de "TCP puro" é exclusivamente o conteúdo do texto
  enviado pelo socket. O HTTP é um protocolo de camada de aplicação definido
  por um formato textual padronizado (RFC 7230). Usamos exatamente as mesmas
  funções socket/connect/send/recv da Aula 2 — o que muda é a string enviada:

    "GET /api/objects HTTP/1.1\r\nHost: api.restful-api.dev\r\nConnection: close\r\n\r\n"

  Essa string obedece ao formato HTTP: método, caminho, versão, headers,
  e linha em branco terminadora. O servidor reconhece esse formato e responde
  no mesmo padrão.

  Se enviássemos uma string arbitrária como "oi, tudo bem?\r\n", o servidor
  HTTP responderia com "400 Bad Request" (não reconhece o método "oi") ou
  fecharia a conexão sem resposta. Nenhuma função de socket retornaria erro —
  o TCP entregaria o texto sem reclamar. O erro seria semântico (camada de
  aplicação), não de transporte.

Questão 4
---------
Por que APIs REST usam TCP e não UDP?

  Uma resposta JSON é uma estrutura de dados com semântica rígida: qualquer
  byte faltando ou fora de ordem invalida o JSON inteiro. Considere o fragmento:

    {"name":"Google Pixel 6 Pro","price":999}

  Se um pacote UDP com "Pro","price":9" chegasse antes de "oogle Pixel 6 ",
  o parser JSON receberia bytes fora de ordem e falharia. Se um pacote com
  "999}" se perdesse, o JSON ficaria truncado e também falharia.

  TCP garante:
    • Integridade: checksums e retransmissão automática em caso de perda.
    • Ordenação: os bytes chegam na mesma sequência em que foram enviados.
    • Entrega confirmada: o cliente sabe que o servidor recebeu a requisição.

  Sem essas garantias, construir uma API REST confiável exigiria reimplementar
  na camada de aplicação exatamente o que o TCP já oferece — reinventar a roda.

Questão 5
---------
A telemetria do drone seria prejudicada se usasse TCP?

  Sim, e de forma significativa. O problema central está na natureza dos dados
  de telemetria: um dado de posição de 1 segundo atrás tem utilidade nula ou
  negativa para controle em tempo real.

  Com TCP, se um pacote de telemetria for perdido, o protocolo trava o envio
  dos pacotes seguintes até retransmitir o perdido (bloqueio head-of-line).
  O resultado é que a central recebe dados de posição com atraso acumulado —
  exatamente o oposto do que se quer.

  Com UDP:
    • Baixa latência: sem handshake, sem espera por ACK.
    • Perda aceitável: o pacote seguinte já tem dados mais recentes.
    • Sem bloqueio: cada datagrama é independente.

  A regra geral: quando "dados velhos são piores que dados ausentes", UDP é
  a escolha correta.

Questão 6
---------
Regra geral para decidir entre TCP e UDP:

  Use TCP quando:
    • Os dados precisam chegar completos e na ordem correta (JSON, arquivos,
      HTML, e-mail, transações financeiras).
    • O cliente precisa saber se a entrega falhou.
    • A perda de qualquer parte dos dados invalida o resultado inteiro.
    • Exemplos: HTTP/REST, FTP, SMTP, SSH, bancos de dados.

  Use UDP quando:
    • A latência importa mais que a perfeição na entrega.
    • Dados antigos perdem relevância antes de poderem ser retransmitidos.
    • A aplicação tolera ou trata perdas ela mesma.
    • O volume de mensagens é alto e o overhead do handshake TCP é proibitivo.
    • Exemplos: streaming de vídeo/áudio (VoIP, Zoom), jogos online,
      telemetria em tempo real, DNS, DHCP.

  Resumo em uma frase:
    "Se você precisa que TUDO chegue certo → TCP.
     Se você precisa que algo chegue RÁPIDO → UDP."
